# InterviewTrace 技术方案草案

## 目标与状态

面向个人 Windows 电脑，提供双来源录音、手动云端转写和本地面试记录管理。优先复用现有库，控制运行依赖，并以录音可靠性为首要验收目标。首版实现已按下列技术栈开发；真实面试设备和云端账号仍需验证。

## 推荐技术栈

| 部分 | 建议 | 用途 |
| --- | --- | --- |
| 桌面界面 | C#、.NET 10 LTS、Windows Forms | 设备和目录选择、录音控制、记录列表、转写展示 |
| 音频采集与回放 | NAudio 与 Windows WASAPI | 枚举设备，录制选定的麦克风和播放设备，回放音频 |
| 记录索引 | SQLite 与 Microsoft.Data.Sqlite | 本地保存手动填写的信息、文件路径和转写状态 |
| 云端转写 | HTTP/JSON 调用阿里云百炼 `fun-asr-flash-2026-06-15` | 用户手动发起，分段上传录音并获取带时间的识别结果 |
| 发布 | .NET 自包含发布 | 打包为 Windows 桌面程序，无需用户额外安装 .NET 运行时 |

桌面程序负责录音和管理；录音与文字保存在用户选择的本地目录，语音识别在云端运行。自包含发布需要携带运行时，包大小和个人电脑上的实际资源占用需要实测，不能仅凭技术栈保证轻量。

## 为什么调整此前的 Python 建议

此前讨论过 Python 和 PyAudioWPatch。核对后发现，PyAudioWPatch 内置的部分播放设备与 loopback 设备对应方法通过设备名称匹配，同名设备可能产生歧义。它仍可用于原型，但不能把该方法当作可靠的唯一设备映射。NAudio 提供 Windows 音频端点枚举，并可将选中的播放端点直接传给 loopback 录音器，更贴合本项目的设备选择需求。

NAudio 和 C# 都不能自动保证录音稳定。需要先在开发机和实际面试电脑上验证设备识别、双路录音与异常处理。若用户更希望主要使用 Python，也可以重新评估 Python 方案并保留相同的设备和可靠性验收标准。

参考：[PyAudioWPatch 设备匹配实现](https://github.com/s0d3s/PyAudioWPatch/blob/master/src/pyaudiowpatch/__init__.py)、[NAudio 设备枚举](https://github.com/naudio/NAudio/blob/main/Docs/EnumerateOutputDevices.md)。

## 音频与记录处理

- 让用户分别选择麦克风输入端点和耳机或扬声器输出端点；设备显示名称用于界面展示，内部尽量使用系统端点标识，并处理标识失效或设备消失的情况。
- 两路音频分别采集和保存，用统一时间基准记录起点及后续数据位置。采样率转换、静音段和长时间采集的时钟偏移都需要验证；不能只按两条文件的开始顺序假定完全同步。
- WASAPI loopback 在输出设备没有播放声音时可能暂时不产生数据。录音处理需要保留该时间段，避免对方沉默导致转写时间线错位。[NAudio 录音说明](https://github.com/naudio/NAudio/blob/main/Docs/WasapiRecorder.md)
- 录音数据持续写入磁盘或分段保存，避免将整场音频存入内存。异常退出后的可恢复范围应通过测试确定；设备故障和写入失败需明确提示。
- 音频与转写文字保存在用户选择的目录。历史记录使用本地 SQLite 索引保存公司、岗位、日期、轮次、文件位置及处理状态；索引文件的实际位置应在设置中清楚显示，并支持用户管理。更改默认录音目录不移动旧文件，也不改变旧记录的实际位置。
- 录音、文件写入和云端请求应在后台进行，避免阻塞界面。日志只记录必要的诊断信息，不记录 API 密钥或面试正文。

## 云端转写

- 用户点击“开始转写”后，两路音频分别按两分钟分段并直接提交；分段前后各保留两秒重叠，识别后根据时间合并并减少边界重复。边界识别仍可能有误，需结合音频复核。
- 阿里云百炼 `fun-asr-flash-2026-06-15` 支持通过 Base64 提交音频并返回带时间信息的结果，单段录音限制需遵循服务文档。此方式不要求额外准备对象存储；计费、网络和模型权限仍依赖云服务。[阿里云接口说明](https://help.aliyun.com/zh/model-studio/fun-asr-flash-recorded-speech-recognition-http-api)
- 两路识别结果应分别检查成功状态并及时保存；失败时保留原音频及已完成的结果，支持用户有意识地重试，避免状态不明时重复提交计费任务。
- 密钥由用户在本机安全配置，不写入源码或日志。具体模型、上传方式与计费规则以实际接入和测试结果为准。

## 原型验证顺序

1. 在真实 Windows 设备上枚举麦克风及播放设备，验证重名设备、默认设备和手动选择。
2. 同时录制两路音频并回放，覆盖耳机输出静音、持续讲话、设备断开等情形。
3. 做 30 至 60 分钟的连续录音试验，检查时间对齐、磁盘占用、界面响应及异常退出后的可恢复内容。
4. 使用实际账号完成一次云端上传、识别、结果合并和导出，核对失败处理与实际费用。
5. 在个人面试电脑上验证打包程序、资源占用、设备兼容以及用户选择的保存目录。
